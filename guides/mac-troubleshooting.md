# Mac Karing 连接故障处理

本页用于客户已授权的 Mac 与 VPS。开发机只读取本文和使用合成输入，不执行网络切换、修复或探测。先读取客户的恢复卡和已尝试项目，保留原值；无效的尝试恢复后再继续。

## 后台测通，切换后 Agent 却掉线

保留旧 VPN，通过新客户端实际 HTTP／混合入口测试新节点。只有 HTTP 确认不可用且 SOCKS5 实测可用时才使用备选，并记录原因。单独测试时暂不开新 TUN 或系统代理，避免两个客户端争抢全机路由。

旧 VPN 尚在运行时的新节点测试只证明当时的连通性，可能仍借用了旧 VPN 的传输路径；切换后必须重新验证，不能直接当成独立线路已通过。

切换前保存具体恢复动作、当前客户端／内核版本与网络栈，进度记为“切换待验证”。掉线先恢复旧连接。恢复后跳过已有的无效尝试，按下面顺序继续。不能用恢复旧 VPN 后收到的回复替代新线路验收。

## TUN 场景先试 mixed 改为 gvisor


AI 打开 Mac Karing「设置 → TUN → 网络栈」，读取当前值。TUN 正在使用 `mixed` 时，记录原值并改为 `gvisor`，保存、重连，随后验证实际 HTTPS 请求与出口。操作期间按本篇网络交接流程保留 Codex 的可用连接，并提前给出具体恢复动作。

修复有效就保留，进入下文验收。无效则恢复原值，继续基础配置核对。已经使用 `gvisor`、没有此选项，或错误发生在未启用 TUN 的本机 HTTP 入口测试中，直接进行基础配置核对。

### 2. 自动校正基础配置

以下步骤由 AI 自行完成，发现具体错误就修正并复测：

1. 备份服务端入站配置、Xray 程序和版本、Karing 节点配置，记录原值与恢复方法。
2. 从面板导出或读取实际节点参数，校正客户端地址、端口、UUID、Flow、传输、SNI、公钥和 Short ID。链接和密钥保存在本机。
3. 检查并恢复 VPS 服务、节点监听及预期端口放行，校正两端时间。读取本次请求对应的日志。
4. 检查本机实际 HTTP 入口和当前代理接管，修正冲突设置。保持可用旧线路，通过 Karing 的指定入口测试新节点；需要线路交接时使用已经准备好的恢复动作。

基础配置修正后仍失败，再评估下文兼容组合。独立 Xray 客户端可作为进一步诊断工具，已有修复流程可以直接推进。


## 兼容组合的适用边界

基础配置正确仍出现 `reality verification failed` 时，有一组已有经验中的配置可供专门评估：

| 配置项 | 兼容排查组合 |
| --- | --- |
| Karing | 1.2.25.2802 |
| VPS 上的 Xray | 26.7.28 |
| REALITY minClientVer | 1.0.0 |
| REALITY 目标 | www.cloudflare.com:443 |
| 两端 SNI | www.cloudflare.com |

这组经验属于旧版本组合。本项目新建默认仍按 [VPS 指南](vps.md) 的 Xray v26.10.31 路线，不自动引入 3x-ui，也不把旧组合当作当前组合已通过的证明。只有普通排错无效、客户授权该服务器版本变更，并评估安全更新与共用入站影响后，才选择一次完整的兼容尝试。保存原程序和配置，保留节点身份，有效则记录，无效恢复。不得对未授权的其他入站或设备一并改动。

本项目不使用旧面板的 receipt 路径或 workflow 命令。变更成功后，在客户本地记录实际版本与 SNI、重导受影响设备的材料；Mac 在本地反馈表标记相关检查失效并重验。

## 修复后的交接验收

- 通过 Karing 实际 HTTP 节点入口访问 `https://www.google.com/generate_204`，取得 HTTP 204，并核对出口为当前 VPS。
- 完成网络交接后，在旧 VPN 已不承载测试流量时验证新 HTTPS 请求、目标出口、Agent 新回复及用户原先失败的操作。
- 系统代理、TUN 接管与全局／规则模式分别核对。本项目需要国内直连时仍使用约定规则模式；全局仅用于已授权的对照诊断或客户选定的全局方案。
- Claude 应用产生新连接并收到新回复后才记实际使用通过。记录未覆盖的 DNS、IPv6、断线行为；未观察到的项目保留待确认。

按 [恢复指南](recovery.md#mac-恢复) 保留本机恢复入口。全部已有方案无效时交回具体脱敏报错、各步结果和当前状态，避免重复切换。
